### 0.8.9.5: A CONNECTION HELD OPEN ACROSS A KEYGEN

`pair` opened a lockdownd connection, fetched DevicePublicKey, and then
generated two 2048-bit RSA keys -- 54180 ms and 17090 ms on the HP --
before sending anything else. lockdownd closes an idle connection, so
the 3728-byte pair request went into a connection the device had
finished with, and the FIN came back as USB_EXFER (-3), the code for a
corrupted packet.

Two rules now:

  - **Nothing holds a lockdownd connection across a computation.**
    `pair` hangs up, generates, and calls back; `lockdown_connect()` is
    idempotent so the call back is free when the connection is still
    up. `tools/check_pair_idle.py` enforces it.
  - **A close is not a fault.** FIN returns USB_ENODEV and
    `usbmux_why()` / `lockdown_why()` say what happened in a sentence.
    A number says which layer gave up, not what the wire did.

The fixture could already send a FIN -- `queue_tcp()` takes any flags.
No check had ever asked it to. That is the third release running where
the gap was a question nobody had put to a fixture that could answer
it (0.8.9.2: a duplicate packet; 0.8.9.4: a 2048-bit key).

### 0.8.9.4: rsa_keygen_step()'s CODES ARE ALL POSITIVE

RSA_KG_WORKING is 1, RSA_KG_DONE is 2, RSA_KG_FAILED is 3.
shell/paircmd.c read them as the USB_OK/negative-errno convention this
tree uses nearly everywhere else -- `if (r < 0)` for failure and
`if (r == 1)` for done -- so it broke out of the loop after ONE step
and copied a key of zero bits. On the HP: "root key: done in 70 ms"
for something that takes 577 steps and half a second, then "a key too
small to pair with" three functions later. shell/rsacmd.c had it right
all along. tools/check_rsa_kg_loop.py refuses both shapes now.

STAGE 2 IS CONFIRMED ON HARDWARE: `GOT THE DEVICE KEY -- 431 bytes`,
`-----BEGIN RSA PUBLIC KEY-----`. Stages 1 and 2 of pairing work on
the HP as of 0.8.9.3.

**AND THE LESSON, which is bigger than the bug:** tests/test_rsa.c had
only ever generated 512-BIT keys -- quick, and the state machine is
the same at any size. Everything in it passed for three releases while
the only caller that mattered was broken. A suite that drives an API
correctly proves the API works and says NOTHING about whether anybody
else used it that way. It generates a 2048-bit key now and asserts the
bit length, because "the generator says done" and "the key is the size
asked for" are two different claims.

### 0.8.9.3: THE LOCKDOWN REPLY BUDGET WAS A POLL COUNT, NOT A TIME

`LD_POLL_TRIES 20000` -- twenty thousand empty bulk-INs finish in
UNDER TEN MILLISECONDS on the HP. A phone answers QueryType at once
and takes longer over GetValue DevicePublicKey, so stage 2 always
timed out and its reply arrived in time to be read as the answer to
the NEXT request. Every reply one behind, for ever, each perfectly
framed and containing the previous question's answer.

Fixed two ways: the budget is TICKS now (get_ticks() is 10 ms UNITS --
this project has got that wrong twice), and **a read that gives up
tears the channel down**, because lengthening a budget cannot make a
late reply impossible and the answer is still coming. ld_send_plist()
has had that rule for a partial send since 0.8.8.10; the read side
never got it.

THE FIXTURE CANNOT REPRODUCE THE SHIPPED DEFECT, and that is recorded
rather than papered over: in tests one poll costs one tick, so a poll
count and a tick count are the same number there. What the suite
checks is the behaviour the fix specifies.

### THE BUG 0.8.9.2 FIXES, AND THE ONE LESSON WORTH CARRYING

`usb/usbmux.c`'s receive path never looked at a packet's SEQUENCE
NUMBER. It added the payload length to the acknowledgement, which is a
count of what this side has seen rather than a position in the
device's stream -- the same number only while every packet arrives
exactly once. So a retransmission was delivered as new data, and on
the HP every lockdown reply came back ONE REQUEST BEHIND: QueryType
answered by the GetValue reply and GetValue by the QueryType reply,
each perfectly framed and perfectly wrong.

**tests/muxdev.inc had never sent the same packet twice.** That is why
5883 checks and 65 injections could not see it. tests/test_xhci.c
records the identical lesson about controller slots -- a resource or a
property that only holds while something never happens needs a test in
which it happens -- and it had not been carried across to the
transport. It has been now: the fixture retransmits, and the checks
were written by reverting the fix and watching them fail first.

### 0.8.9: STAGE 3 IS FINISHED, AND ONE QUESTION IS LEFT

**`pair` IS THE FIRST THING TO RUN ON THE HP**, and it now goes all
the way: the Trust dialog, the record saved to `.pairrec`,
StartSession, a TLS handshake presenting our host certificate as a
CLIENT certificate, and one QueryType sent inside the encrypted
session as proof. It prints `STAGE 3 IS COMPLETE.` or the step it
stopped at.

**THE ONE THING THE TESTS CANNOT ANSWER.** This stack offers exactly
one cipher suite -- `TLS_RSA_WITH_AES_128_CBC_SHA256`, static RSA key
exchange. `openssl s_server` is happy to negotiate it; iOS lockdownd
may not be. That is the single most likely way the hardware test
fails, it is a capability limit rather than a bug in the pairing, and
`tlsinfo` is built to say so -- it prints the suite the peer chose and
the alert number beside it. Part 4 of
`docs/PAIRING-STAGE3-HARDWARE-TEST.md` says exactly what to photograph.

**`net/tls.c` TAKES A TRANSPORT NOW.** It spoke to `net/tcp.c` by name
in nine places, and the lockdown session runs over a usbmux channel
which has no fd. The transport and the client certificate belong to
the SESSION SLOT rather than to a global, because an HTTPS fetch and a
lockdown session can be open at once and a global would send one
session's records down the other's channel -- with both ends reporting
success.

**THE PAIR RECORD HOLDS TWO PRIVATE KEYS, UNENCRYPTED**, on the system
volume at `.pairrec`. There is nothing in this kernel to encrypt them
with. What they can do is bounded: they pair with phones already
paired from this machine. `pair forget` deletes it. `pair show` prints
what is stored.

**`signature_algorithms` WAS MISSING FROM THE ClientHello**, and RFC
5246 7.4.1.4.1 makes that mean "{sha1, rsa}" -- the one thing this
stack cannot sign with. It cost nothing while no CertificateVerify was
ever sent; the first client certificate would have been refused for a
reason nowhere near the certificate.

**THREE FINDINGS ABOUT THE TESTS THEMSELVES**, all in
`CHANGELOG-v0.8.9.md` and all the same shape -- a check that passed for
the wrong reason:

1. `openssl s_server -Verify` **accepts a chain it failed to verify**
   unless `-verify_return_error` is given. For one run the main case of
   the new suite was passing against a judge that was not judging. The
   negative control found it.
2. **Two harnesses existed only as prose.** `net/b64.c` records
   nineteen injections and `usb/pair.c` twenty-seven; neither was ever
   written down as a runnable harness, so none of the forty-six could
   be run again. `tools/check_b64_suite.py` and
   `tools/check_pair_suite.py` now exist.
3. **Seven injections had gone stale** in
   `tools/check_lockdown_suite.py` -- one when 0.8.8.10 replaced
   `usbmux_send()`, six when 0.8.8.11 deleted the base64 decoder they
   aimed at. `inject.py` reports a stale injection rather than counting
   it, which is the only reason any of it surfaced.

New files: `tests/test_tlscc.c`, `tools/check_tls_stages.py`,
`tools/check_tlscc_suite.py`, `tools/check_b64_suite.py`,
`tools/check_pair_suite.py`, `docs/PAIRING-STAGE3-HARDWARE-TEST.md`.

### BETA 12: THE TRACKPAD, AND THE PAIR REQUEST

**`i2chid` IS THE FIRST THING TO RUN ON THE HP.** One screen, made to
be photographed. The ACPI blocker that stopped the trackpad for five
releases turned out to be dodgeable: an I2C-HID descriptor's first
four bytes are always `1E 00 00 01`, so the descriptor register can be
PROBED rather than looked up in AML -- try the handful real hardware
uses, accept the one where what comes back IS a descriptor. If nothing
is found, `i2chid` rescans and lists every address that DID answer,
because "the bus works and the register guess was wrong" and "the bus
is dead" need different next steps.

**`pair` IS THE SECOND.** It asks the phone to trust this computer:
two 2048-bit keys, three certificates (the third certifies the
DEVICE's public key with our root), and a five-kilobyte plist. The
phone should put a Trust dialog on screen. The reply says in words
what happened. (**The record is saved as of 0.8.9** -- this paragraph
describes beta 12, where it was not.) `pair` prints the elapsed time
per key, which is the keygen measurement nobody has ever taken on the
HP.

**A USB mouse used to freeze the machine on a right-click in
Notepad.** `do { mouse_get(...) } while(mb&2);` with nothing in the
loop polling USB and nothing reading the keyboard. `mouse_get()` and
`mouse_get_clicks()` now drain both polled buses, and that loop is
bounded with an ESC out of it. A whole class of consumer -- anything
reading clicks but not keys, like `shell/chat.c` -- never saw USB
input at all.

**Four base64 implementations became one** (`net/b64.c`), and two of
the four took no output capacity at all: `cmd_base64_v3()` with a
384-character argument wrote 513 bytes into a 512-byte array.

New files: `net/b64.c`, `net/der_read.c`, `usb/hid_rd.c`,
`drivers/i2c_hid.c`, `usb/pair.c`, `shell/i2chidcmd.c`,
`shell/paircmd.c`. Five new suites, all under ASAN where a sweep makes
it meaningful.

### THE VERSION NUMBER WENT BACKWARDS ONCE, ON PURPOSE

This drop was built as **0.8.9** and renumbered to **0.8.8.10** at
Kyan's request, to keep Helios inside one version. `ver_cmp()` compares
component by component, so:

```
0.8.8.10 vs 0.8.8.9  ->  1    the update IS offered
0.8.8.10 vs 0.8.9    -> -1    a DOWNGRADE
```

**A machine that already ran `update` to 0.8.9 will not be offered
0.8.8.10 or anything else in the 0.8.8.x series.** It has to be
reinstalled from an ISO. Nothing was shipped as 0.8.9 beyond the one
bundle, so this matters only if that bundle was applied. It is written
down because the next person to renumber a release needs to know the
trap is real and which direction it bites.

### BETA 11: PROPERTY LISTS, AND A MESSAGE BIGGER THAN A PACKET

No new command and no new screen. Stage 3 pieces two and three:

* **`net/plist.c`** writes Apple property lists -- every lockdownd
  message is one, and until now they were string constants in C
  source. The pair request carries three certificates and cannot be
  a format string. Judged by **Python's `plistlib`**, because there
  is no plist reader in this tree and a writer checked against our
  own reader would prove nothing. 93 checks, 23 injected defects, 19
  caught; the four survivors are written down at the end of the file
  and all four are properties of XML rather than gaps.
* **`usbmux_send_stream()`** splits a request across packets.
  `ld_send_plist()` used to refuse anything over 2012 bytes BY NAME
  with "not written yet" -- that refusal is gone. `LD_REQ` is 12288.
  Data that arrives mid-send is stashed and returned before anything
  newer, because those bytes are already acknowledged and the device
  will not send them again.
* **The device's window is warned about, not blocked on.** The reason
  is in `usb/usbmux.c`: the device advertises 131072 bytes, so an
  enforcement path would never run, and an unexercised blocking path
  in a transport is how a working transfer becomes a hang. The
  overrun is counted and logged instead, and `usbmux` prints it.
* **A partial send tears the connection down.** Once segments are
  out, lockdownd is mid-length-prefix and every later request is read
  at the wrong offset with nothing reporting an error. A failure with
  NOTHING on the wire deliberately does the opposite: the stream is
  still aligned and the channel is kept.

**`tests/muxdev.inc` can now hold two packets in flight**, which is
what made the "do not harvest while the stash is occupied" guard
reachable at all, and the fixture now accumulates the host's whole
byte stream -- a segment sent twice with another dropped keeps the
byte count right and shows up nowhere else.

### BETA 10: `uninstall`, AND CERTIFICATES

**`uninstall` IS A SHELL COMMAND NOW.** Boot the ISO, type it. Dry-run
preview, then the word `UNINSTALL` typed in full. It finds our
partition BY TYPE GUID, restores `\EFI\BOOT\BOOTX64.EFI` from
`BOOTX64.HDB`, removes `\EFI\HAVENDOS`, clears the table entry, and
removes the ESP only if WE made it (label `HAVENBOOT` AND no
`\EFI\Microsoft`). It will not touch a fallback loader that is not
ours. It does not erase the partition's data.

New underneath: `gpt_remove_partition()` (index AND type GUID AND
first LBA must all match, or nothing is written) and `fat32_rmdir()`.
`test_installadd` is 151 checks and the headline one is a ROUND TRIP:
install, uninstall, and the foreign loader comes back byte-for-byte.

**PAIRING STAGE 3 HAS STARTED.** `net/x509.c`: X.509 v3 certificates
signed PKCS#1 v1.5 over SHA-256, which finally gives `net/der.c` a
caller. `test_x509` is 45 checks and every verdict is `openssl`'s --
`x509` to parse, `asn1parse` for DER, and `verify` for the signature.

**ONE INJECTION GOT THROUGH THE FIRST VERSION OF THAT SUITE** and is
worth knowing about: encoding the signature at its own byte length
instead of the modulus length is correct 255 times in 256, so one key
and one digest will not catch it. The suite now SEARCHES for a
signature with a zero top byte (~256 signings) and requires the
leading zero to survive. If you add a crypto suite, assume one
sample proves nothing about a 1-in-256 defect.

**STAGE 3 IS NOT FINISHED.** Certificates are one of four pieces. Still
needed: a plist WRITER, splitting a request across mux packets
(`ld_send_plist()` refuses a multi-packet request by name), the
pair-record exchange, and TLS WITH CLIENT CERTIFICATES -- `net/tls.c`
is an HTTPS client and does not do them.

### BETA 9, THE TWO THINGS TO KNOW

**1. THE PIT WAS COUNTING AT TWICE REAL TIME, AND NOW IS NOT.**
`kernel/pit.c` programs channel 0 in mode 3 (`outb(0x43,0x36)`),
where the 8254 decrements the counter by TWO per input clock.
`pit_us()` treated a counter delta of N as N clocks, so it reported
double the elapsed time -- and `sleep_ms(100)` slept about 52 ms,
`get_ticks()` ran at 200 Hz, and every `dmesg` timestamp was
inflated. Every network timeout, retransmission timer, animation
delay and the screensaver countdown was half its nominal value.
Fixed by halving one constant (54927 -> 27464). **Durations
everywhere in the tree are now twice what they were in practice**,
which is what their call sites always asked for; if something that
was tuned by eye now feels slow, that is why.

No suite caught it and none would have: every timing test in the
tree measures the PIT against itself. It was found by screenshotting
a boot with host-clock timestamps.

**2. HAVENDOS CAN NOW INSTALL ON A DISK WITH NO OTHER OS.**
`fs/fat32fmt.c` (a FAT32 formatter, there was only FAT16) and
`fs/espmake.c` (survey + create). The installer reserves 100 MB at
the FRONT of its gap, makes an EFI System Partition there and puts
HavenDOS after it. The boot entry is `\EFI\BOOT\BOOTX64.EFI`, the
firmware fallback path -- no Windows, no bcdedit.

It never consumes an existing partition. An unrecognised partition
with no filesystem signature is REPORTED as a candidate and left
alone; "we did not recognise it" is not "it is empty".

A NAMED NVRAM boot entry is NOT possible from here and the reason is
in `include/espmake.h`: `SetVariable()` is a UEFI runtime service and
a multiboot 1 kernel never receives the EFI system table. It needs
the multiboot 2 EFI handoff, which is a boot-path rewrite.
Nothing native was added in beta 8 on purpose -- every display fix in
it is a coordinate, and a native test that computes a coordinate from
the same macro the kernel uses agrees with itself by construction.
The new evidence is a harness and a control build instead.

### BETA 8: THE ISO DID NOT UEFI-BOOT, AND A CHECK SAID IT DID

Booted under OVMF, the v0.8.8.6 ISO gave `BdsDxe: failed to load
Boot0001 ... Not Found` and fell through to PXE. It carried only
`BOOTIA32.EFI`; an x86_64 machine looks for `BOOTX64.EFI` and nothing
else, and the HP has no CSM to fall back to. `grub-mkrescue` emits
whichever the installed GRUB platform packages allow, so this
depended silently on `grub-efi-amd64-bin` being present in the build
container. `check_iso_bootable.py` now reads the PE machine field out
of the loader on the EFI image and fails the build unless it is
0x8664. Four injections prove it fails for the right reason; a fifth
proved the injection wrong rather than the check and is recorded in
`CHANGELOG-v0.8.8.7.md`.

**OVMF IS INSTALLED IN THIS CONTAINER** (`/usr/share/OVMF/`), and a
previous session claimed it was not. UEFI boots CAN be tested here:
`python3 tools/uefi_boot.py <image> <out-prefix> [--secs=N]
[--keys=ret@20]` boots an image under real firmware and screenshots
it.

### BETA 8: THE gfxmode LIST NEVER REACHED THE KERNEL

GRUB honours the mode in the kernel's own multiboot header
(`boot/boot.S`, `FB_WIDTH`/`FB_HEIGHT` = 1280x800) ABOVE `gfxmode`
and `gfxpayload`. The list beta 7 added to `isodir/boot/grub/grub.cfg`
styles GRUB's menu and stops there -- measured by forcing it to
1920x1080 and still booting 1280x800.

That is the real cause of the 64x24 console: 1280/16 x 800/32 is
exactly 80x25, so it looked right everywhere that can do 1280x800.
The HP cannot, GRUB fell back to "auto", and that gave 1024x768.
Setting the header to 0 ("no preference") is WORSE -- GRUB then skips
the list and "auto" gave 800x600. Both files now say so.

### BETA 7 IS ONE FINDING, AND `layout` FOUND IT IN ONE LINE

His panel is 1024x768. The readable 16-pixel cell gives **64x24** --
SMALLER than the 80x25 every app lays out for -- and beta 6's
`resolution fit` offered it, he took it, and it was saved. A console
under 80x25 cannot be rescued by the viewport: there is nowhere to
centre an 80x25 box inside it.

Measured on a booted ISO: **21 apps draw outside at 64x24, none at
80x25.** Text Editor overflowed by the same 50 cells his machine
reported, which is as exact a reproduction as this project has had.

`vga_fb_app_grid()` is the policy now -- readable cell if the grid is
still at least 80x25, a smaller cell if that is what it takes, a
refusal if the panel cannot do it at all. 1024x768 gets **128x48**. A
saved grid under 80x25 heals itself at boot, once and loudly, because
it could only have been chosen because this OS offered it.

**AND AN ISO WITH AN EMPTY grub.cfg USED TO PASS EVERY CHECK.** Found
by deleting the file and expecting the build to regenerate it; it did
not, and `check_iso_bootable` said ok because the El Torito catalog
was intact. It reads the menu out of the ISO now. The first version
of that check failed the REAL ISO -- `xorriso -extract ... -` returns
0 and writes nothing -- which is worse than the gap it closed, and it
was caught only by extracting the file by hand.

### THE HP ANSWERED BETA 5, AND IT CLOSED THE OLDEST OPEN ITEM

`claude/havendos-0.8.8.4-on-the-hp.md` has it in full. Three findings:

1. **THE 32 GB STICK ENUMERATES.** `port 12: 0951:1666 class 08` then
   `USB MSC Kingston DataTraveler 3.0: 29560 MB`. The item that has
   been top of this list since v0.8.6 is CLOSED. **Reading it is
   still unproved** -- `FAT16: mounted` is the installed partition on
   the NVMe, not the stick.
2. **THE APP GUARD HELD ON REAL SILICON.** `appguard: Shell faulted --
   divide by zero at 001794E9`, and the prompt came back.
3. **I2C HAS NO BAR.** The firmware assigned the two Serial-IO
   controllers no memory window at all, and `00:1F.5` is the SPI
   controller sharing the class code. The trackpad is unreachable
   because there is nothing to talk through -- so the next step is
   PCI resource assignment, which this kernel has never done.

### AND THE ANSWER ON GRAPHICS AND 64-BIT

`claude/havendos-xe-graphics-and-64bit.md`, in full. The short form:

- **An Xe driver is not reachable.** Signed GuC/HuC firmware, GGTT and
  PPGTT, a command streamer, and per-generation display hardware
  whose programming guide is not published in a usable form. It is
  not a hard feature; it is a different project, and it is the one
  item that would consume everything else to find that out.
- **The GPU is already the framebuffer.** `Framebuffer 1280x800 32 bpp
  at FD000000` IS the Xe display engine, programmed by the firmware.
- **More RAM needed no 64-bit at all** and is done -- see below.
- **64-bit is tractable and is its own release.** It buys above-4 GB,
  64-bit bignum limbs, and the ecosystem. It costs a new boot path,
  4-level paging, every assembly stub, and an audit of every
  `uint32_t` used as a pointer in a tree that has been carefully
  32-bit its whole life. PAE is the wrong intermediate step for a
  single flat address space.

### WHAT BETA 5 CHANGED, AND THE FIVE BUGS BOOTING IT FOUND

`CHANGELOG-v0.8.8.4.md` has all of it. The short form:

1. **An app crash no longer panics the machine.** `kernel/appguard.c`
   plus a `crash` command that faults on purpose, because a recovery
   path is the one kind of code a native suite cannot reach.
2. **Apps are no longer nailed to 80x25.** A VIEWPORT in
   `drivers/vga.c`: `vga_cols()` lies to an unconverted app and its
   coordinates are translated into a centred box. No app was
   modified. `appreg_t.fits` marks the two that do use the real grid.
3. **The Windows key** opens the start menu. It was being discarded by
   both keyboard drivers.
4. **A loading screen** driven by `klog()` rather than a timer, with
   the current init step as its caption.

### WHAT 0.8.8.2 DID

`CHANGELOG-v0.8.8.2.md` is the long version.

**1. THE TEXT WAS STRETCHED, AND IT WAS NOT THE SCALER.**

`fbc_fit()` picked the glyph scale separately per axis: 1280x800 at
80x25 gave sx=2, sy=4, so every character was drawn sixteen pixels
wide and THIRTY-TWO tall. On 1920x1080 it was 3 and 5.

The scale factors were not the mistake. **80x25 of 8x8 cells is
640x200, an aspect ratio of 16:5**, and no panel is that shape, so no
pair of equal scales can fill one. 80x25 of **8x16** cells is 640x400
— 16:10, and 1280x800 divided by exactly two in both axes.

So: `include/font8x16.h`, generated by `tools/make_font8x16.py` from
`koi8x16.bdf` (X11 font-misc-cyrillic, "may be distributed and
modified without restrictions", quoted in the header — same
arrangement as `font8x8.h`, which is Hepper's public-domain font8x8).
And `fbc_fit()` now takes the **minimum** of the two scales and
centres the remainder, because a square cell is not negotiable and
filling the panel is.

**"Switch to real graphics" would have changed nothing.** The console
already IS a framebuffer. What was wrong was the shape of the cell.

Consequences: 240x135 no longer fits 1080p (135 rows of 16 pixels is
2160 scanlines); 2560x1440 is no longer "capped"; `resolution fit` on
1280x800 lands on exactly 80x25, which is what that panel wants.

**The text console is untouched** — its 80x50 mode uploads 8 rows
into plane 2 and that hardware wants exactly 8.

**2. THE DESKTOP ICON GRID WAS TWO COLUMNS AT ANY WIDTH.**

The literal 2 in five places in `shell/desktop.c`. The chrome already
scaled from `vga_rows()`/`vga_cols()`; the icon field did not, so 45
of 80 columns were empty and 85 of 120. One `icon_cols()` now, because
`icon_hit()` and `draw_icons()` disagreeing means clicking one icon
and launching another.

**3. THE 32 GB STICK: THE UPDATER READ FAT32 ONLY.**

Reported four releases running. `fs/update_src.c` called
`fat32_scan_volumes()` and nothing else, and `update` said so in small
print. **A stick of 32 GB or more is exFAT by default.** FAT32 is
still tried first; exFAT is the fallback. Safe for the same reason
FAT32 is and FAT16 is not: it is a separate driver with its own mount
slot, and `fs/update.c` writes the system volume through `fs/fat16.c`.

**4. A LIVE BUG IN THE PRIMALITY TEST — see the stage 3 section.**

**1. THE MOUSE WORKS — AND IT WAS NEVER THE POLLING.**

`mouse_is_ready()` returned a single flag set only by the PS/2 reset
handshake. On a laptop whose trackpad is not behind the 8042 — most of
them since about 2012 — nothing acknowledges that reset, the flag
stayed 0, and the desktop never read the pointer. **A USB mouse was
enumerated, claimed and polled correctly, and then ignored**, because
the only thing that could set the flag was a port that was not there.

Readiness now has two sources: `ps2_ready || usb_pointers > 0`, with
the USB count rebuilt from what is present on each enumeration rather
than incremented across rescans.

The boot log said `mouse polled (8042 IRQ12 off)` on a machine with no
PS/2 mouse. It now says **`no mouse answered the aux port (a USB mouse
still works)`**, which is the line that would have made this a
five-minute diagnosis instead of a release.

**The polling was wrong too, but less than it looked.**
`kernel_poll()` ran from `keyboard_waitchar()`'s idle loop and the
desktop calls `keyboard_getchar()`, so in the desktop the bottom half
never ran at all. It is now in `getchar()`. It is deliberately **not**
in `keyboard_haschar()` — that is a predicate, callers use it in tight
loops, and work that runs from a predicate runs at a depth nobody
counted.

**2. exFAT, READ-ONLY, AND THE CONSOLE GRID PERSISTS.**

`fs/exfat.c`: both cluster walks, because exFAT has two and a reader
that handles one is wrong about half the time in a way that looks like
a corrupt disk. `exfat` reuses `fat_scan_volumes()` with a
`FATTYPE_EXFAT` filter rather than walking the partition table again.
Writing needs the allocation bitmap kept in step with the FAT and is a
release of its own; `include/exfat.h` has no write function in it.

`resolution 100x50` now survives a reboot — it was applied and never
written down. Saved only on a **confirmed** mode change, because the
confirm prompt exists so an unreadable grid can be backed out of, and
saving before confirmation would persist exactly the grid that broke
the screen. `resolution fit` picks a grid with at least 16 pixels per
cell: 1280x800 → 80x50, 1920x1080 → 120x67, 3840x2160 → 240x135.

**There is still no 8x16 font in this tree** — not one byte of glyph
data for it. `fit` doubles the 8x8 and looks doubled, which is the
honest half of "make everything size better".

**This one needs a decision, not more code.** Drawing 256 glyphs is a
day's work. Taking an existing bitmap font is faster and is a
**licensing choice** — it is Kyan's to make, not mine, and I am not
going to pull a font into the tree on his behalf. Until then `fit` is
what there is.

**3. net/bignum.c — AND THE TWO DEFECTS ITS SUITE CAUGHT.**

Limb arithmetic with Montgomery reduction, checked against CPython and
`openssl genrsa`. `rsa_public_encrypt()` moved onto it, so TLS key
exchange stops pausing. **The suite did not pass first time — 273 of
277 — and both failures were real:** see "THE BIGNUM, AND WHY IT IS
TRUSTWORTHY" below. Those two are the most useful thing in this
release to read before writing any more arithmetic.

**1. THE CONSOLE CAN EXPRESS ANY GRID — CHOSEN BY THE USER, NOT AT BOOT.**

`VGA_COLS_MAX` was 90 and `VGA_ROWS_MAX` 60 because 720 pixels over an
8-dot character clock is 90 columns and 480 scanlines over an 8-line
cell is 60 rows. Those are facts about a CRTC, and `fbc_fit()` clamped
the **framebuffer** grid to them while `vga_set_mode()` refused anything
that was not one of the four text modes **before looking at which
console was active**. On a machine with no text memory, the thing
deciding how much screen HavenDOS could use was a register table that
machine cannot execute.

Now: any grid inside 320x180 and 32400 cells, on a framebuffer; the
four register sets, untouched, on VGA text memory. `resolution` takes
`CxR` and `max`, and a refusal says **which** of the four limits it hit.

**AND THE AUTO-DETECT IS DELIBERATELY ABSENT.** See "WHAT RM-1003 ASKED
OF HELIOS" below. The boot grid is still 80x25 and the desktop still
pins 25 rows, so nothing regressed — which is the whole reason the
auto-detect is not here.

**2. SOMETHING RUNS ON A TIMER.** `kpoll_tick()` in IRQ0 counts and sets
due flags; `kernel_poll()` runs the work from the keyboard's idle loop.
Three clients: DHCP retry with backoff, carrier transitions, and USB
hot-plug off the root ports.

The phrase *"nothing in this kernel runs on a timer"* is gone from this
file and from the source.

**AND IRQ0 IS CONFIRMED ARRIVING.** The tick count climbs — about 825
ticks over four seconds in QEMU, which is 100 Hz give or take a TCG
host under load. That is the first evidence this project has had that
IRQ0 reaches a handler at all; `kernel/idt.c` records that
`irq_common_stub` was missing its `push %esp` for an unknown number of
releases and nothing noticed, because nothing depended on it.

The boot log of every run now carries:

```
[   3.141]  ok  kpoll: 3 periodic task(s) at 100 Hz
[  28.874]      dhcp: no address yet, asking again (try 1 of 5)
```

That second line is a retry nobody typed, twenty-five seconds after the
one-shot at boot gave up.

**3. THE BOOT LOG'S IRQ12 CLAIM — AND THE NOTE ABOUT IT WAS WRONG TOO.**

The previous handoff said the slave PIC stays masked, so IRQ12 cannot
fire. **That is false.** `irq_enable_mouse()` unmasks IRQ12 *and* the
cascade, and `kernel/main.c` calls it on the line immediately before
printing that entry.

Three layers have to agree, and the PIC is only the middle one:

1. **the 8042 must generate it.** `drivers/mouse.c` clears bit 1 of the
   config byte — *"IRQ12 stays off, we poll instead"*. So it never does.
2. **the PIC must not mask it.** This layer was fine.
3. **something must be registered for it.** Nothing is.

A note blaming layer 2 would have sent somebody to edit the one layer
that was innocent. **A recorded gap is a hypothesis, not a finding** —
v0.8.7.6 wrote down that it could not tell `tx_seq` from `rx_seq` and
was right that the check was impossible and wrong about why.

The line reads `PS/2: keyboard on IRQ1, mouse polled (8042 IRQ12 off)`,
and `check_boot_log.py` refuses a boot log line claiming work on an IRQ
nothing registers a handler for.

### WHAT BOOTING 0.8.8 FOUND THAT NO SUITE COULD

Four things, and `harness/helios_boot.py` exists because of them.

**A PERIODIC CLIENT'S LOG LINE LANDS ON TOP OF THE SCREEN.** The first
boot after wiring the clients up printed a DHCP retry over `dmesg`'s own
pager prompt:

```
-- more -- (any key, Q to stop)[  28.874]      dhcp: no addre
ss yet, asking again (try 1 of 5)
```

`klog`'s live echo was safe only for as long as every call came from a
driver bringing itself up, before anything was on the screen. The
clients log from `kernel_poll()`, which runs at exactly the moments the
screen belongs to somebody else. `include/klog.h` says the echo exists
so a kernel that dies halfway through init has already said how far it
got — an argument about **init** — so `kernel/main.c` calls
`klog_set_echo(0)` after "System ready" and the ring is what `dmesg`
reads.

**THE FRAMEBUFFER TEXT DECODER ASSUMED THE GRID FILLS THE SCREEN.**
`harness/fbtext.py` computed a cell as `W//cols` by `H//rows`.
`drivers/vga.c` picks an integer scale per axis and **centres** the
result. On 1280x800 at 80x25 the two agree, and that is the only panel
QEMU has been run at here. On 1366x768 the old arithmetic drifts a pixel
per column and the decode turns to noise a third of the way across. It
surfaced because `resolution 100x50` is a 1x2 scale with 240-pixel
margins, and the harness read a working screen as ASCII art.

**TWO COMMANDS PAGE, WITH TWO DIFFERENT PROMPTS.** `dmesg` stops with
`-- more -- (any key, Q to stop)`, `help` with `-- more -- press any
key --`. The harness typed the next command into the open pager twice:
`kpoll` was swallowed whole, and `resolution reset` arrived as `ution
reset` with its first three characters consumed as the keys that
dismissed three pages. **The shell then reported a command that does not
exist**, which reads nothing like an unread prompt. And the obvious fix
is wrong: `-- more --` stays visible after a key dismisses it, so it has
to be the **last** thing on screen.

**THE CONSOLE IS SLOWER AT A BIG GRID.** 100x50 on 1280x800 is 5000
cells of 8x16 physical pixels per repaint. A person types at five
characters a second and will not see it; a harness at twenty can.

### STAGE 1, THE BOOT BEFORE IT

**31 October, on the HP:**

```
ok  lockdown: LOCKDOWND ANSWERED -- com.apple.mobile.lockdown
    reply: 301 bytes in 1 packets
    length prefix: 00 00 01 29 = 297
```

The first time this kernel has talked to a **service** on the phone
rather than to its mux. Four things settled with it:

- **the length prefix does not count itself** — 297 declared against a
  301-byte reply, the opposite of the mux header four bytes below it
- **`seq 286 ack 302`** = 1+285 and 1+301: the ack arithmetic is right,
  and so is acking at ISN+1 rather than usbmuxd's `tx_ack++`
- **`their window 131072`** — the `<<8` on the way in is right
- **`errs 0`**

**AND ONE CORRECTION.** `reply: 301 bytes in 1 packets`. The
accumulator in `usb/lockdown.c` was built because libimobiledevice's
`internal_plist_send()` writes the length and the body as two separate
`service_send()` calls. **The device does not** — it sends them
together, and a reader written for one packet would have worked. The
accumulator stays (it handles both, the one-packet case is tested as
the contrast, and a reply larger than the window arrives in pieces
anyway) but the stated reason was about upstream's HOST side and did
not transfer to the device. **An argument about one end of a protocol
is not evidence about the other.**

**v0.8.7.9 adds stage 2**: GetValue for DevicePublicKey, same
connection, no cryptography. `usb lockdown` runs both.

### WHY HELIOS CAME FIRST — AND THE MEASUREMENTS THAT SCOPE STAGE 3

**Decided with Kyan, 31 October, and Helios has now shipped.** Stage 3
is the pair request, and it is several releases of security-critical
code rather than one more request. Two things were established before
deciding, and they are the scope of stage 3 rather than a reason to
delay it any further:

**1. THE EXISTING BIGNUM CANNOT DO KEY GENERATION — not slowly, at
all.** `net/tls_crypto.c` has `bn_powmod()` and `rsa_public_encrypt()`
and that is all. There is **no general multiply, no division and no
modular inverse**, and keygen needs all three: `phi = (p-1)(q-1)` is a
full multiply, and `d = e^-1 mod phi` is an inverse.

What is there is BYTE-WISE double-and-add, which was fine for its one
job (e=65537 is 17 bits). Measured, compiled -O2 on a fast container
CPU, 2048-bit modulus:

```
modexp, 17-bit exponent (e=65537)      0.163 s
...per exponent BYTE                   0.073 s
=> a 2048-bit private exponent          18.6 s
=> one Miller-Rabin round, 1024-bit     ~2.3 s
```

So 30-60 s per private-key operation on the HP, and **RSA-2048 keygen
is roughly 15-25 minutes** — four 1024-bit primes, each ~35 candidates
surviving trial division into Miller-Rabin.

**2. UPSTREAM NEEDS MORE THAN ONE KEY.** libimobiledevice's
`common/userpref.c`, `pair_record_generate_keys_and_certs()`: **two
RSA-2048 key pairs** (root and host), **three X.509 v3 certificates**
with critical basicConstraints and keyUsage extensions, all **SHA-256
signed**, in a PairRecord with HostID and SystemBUID.

So stage 3 is: a limb-based bignum, Miller-Rabin, RSA keygen, a DER
encoder, an X.509 v3 builder, PKCS#1 v1.5 signing, a plist WRITER, and
splitting a request across mux packets -- `ld_send_plist()` refuses a
multi-packet request by name today. Plus suites and injection
harnesses for all of it, because **a broken RSA that looks like it
works is the worst outcome this project could produce.**

**AND THAT WAS WHY HELIOS CAME FIRST, which it now has.** A 15-25 minute keygen on a
kernel where nothing runs on a timer is a completely frozen machine:
no progress, and no way to tell a slow prime search from a hang.
0.8.8's tick and `kernel_poll()` are exactly the fix, and they exist
now: the keygen yields through `kpoll_sleep_ms()`, shows progress and
stays interruptible. Building the one
feature most likely to LOOK like a crash, on a kernel that cannot tell
you it is not one, is the wrong order.

**When stage 3 does start, the bignum is the first piece.** It is pure
logic, testable natively against published RSA test vectors with no
phone involved, and it makes TLS faster as a side effect. Nothing
about it is wasted by waiting.

### AND THE MAGIC IS 0xFACEFACE

**30 October, on the HP. Stage 1 got further than any suite could show
and was refused over one constant.**

```
usbmux: SYN -> port 62078, from 18516
warn usbmux: magic FACEFACE, expected FEEDFACE
warn usbmux: the SYN/ACK was unreadable (-3)
```

and the packet `usb mux` showed afterwards:

```
last packet: 36 bytes
00 00 00 06 00 00 00 24 FA CE FA CE 00 00 00 01
```

protocol **6 (TCP)**, length **36** = 16 header + 20 TCP, magic
**FACEFACE**, and `rx_seq 1` mirroring our SYN's `tx_seq`. **That is
the SYN/ACK.** The phone parsed our mux header, our TCP header, the
port and the sequence number, and answered.

**usbmuxd never reads the magic.** `src/device.c` has exactly two
occurrences: the struct field, and `send_packet()` writing it on the
way OUT. `device_data_input()` validates the LENGTH and nothing else.
The host writes 0xFEEDFACE, the device writes 0xFACEFACE, and nobody
notices because nobody looks.

Fixed in v0.8.7.8: the magic is read and reported, never believed.

**How it got in matters more than the fix.** The check was not written
for stage 1 — it came from v0.8.7.3 guarding the VERSION exchange, and
v0.8.7.6 correctly scoped it to the sixteen-byte header. All of that
was right. **It had simply never run against a real packet**, because
stage 0 only ever received a VERSION reply, which uses the eight-byte
header and skips it. Stage 1 is the first sixteen-byte-header packet
this kernel has ever received from a device, and the check failed on
the first one.

v0.8.7.7's changelog says every deliberate departure from usbmuxd is
marked and argued, and lists two. **This was a third, undeclared, and
it arrived by carrying a guard forward rather than by adding one. A
departure you inherit is still a departure.**

That was 30 October. The next boot closed stage 1 — see the top of
this file.

**`docs/HELIOS-HARDWARE-TEST.md` is 0.8.8's five minutes on the HP**,
and the one line in it that can change the road is the tick count: if

### WHAT 0.8.7.7 FIXED THAT NOTHING HAD EXERCISED

**Three sequence-number rules in the mux header, all three wrong.**
`tx_seq` and `rx_seq` read like counters and neither is one:

- `tx_seq` advances only on a packet that CARRIES it, so the VERSION
  packet must not move it. 0.8.7.6 advanced unconditionally.
- the SETUP packet RESETS the pair — tx to 0, rx to 0xFFFF — and writes
  those values before advancing. 0xFFFF is "nothing received yet".
- `rx_seq` is the device's own rx_seq field mirrored straight back, not
  a tally of arrivals.

0.8.7.6 sent `tx 1 rx 1` where usbmuxd sends `tx 0 rx FFFF`.

**Why nothing caught it, and the lesson.** The only sequenced packet the
kernel had ever sent was one SETUP, and the two wrong rules happened to
produce the same number for both fields. The suite asserted 1 and 1 and
the driver obliged. The file even recorded that it could not tell the
two fields apart — **it was right that the check was impossible and
wrong about why.** Two wrong values that happen to be equal look exactly
like a field you cannot test.

`usb mux` prints the pair now. After a SETUP and nothing else it reads
`mux seq: tx 1 rx FFFF`.

**And the harness found a real bug while establishing why a fourth
injection could not fire: a SETUP that failed to send was never sent
again.** The VERSION is answered, the version becomes 2, the header
becomes sixteen bytes, the SETUP fails — and `usbmux_handshake()`
returned the known version unconditionally for ever after. A channel
permanently out of step with the device, reporting itself healthy.
`usb mux` twice in a row is the path that reaches it. The setup is owed
until it gets out.

### THE PROTOCOL IS NO LONGER A GUESS

0.8.7.3 shipped a sixteen-byte header because it **reasoned about** the
protocol. Everything added in 0.8.7.7 was read out of the two
implementations known to work against a real device — usbmuxd's
`src/device.c` for the mux and its TCP, libimobiledevice's
`common/property_list_service.c` and `src/lockdown.c` for the plists.
The interface triple FF/FE/02 matches usbmuxd's `src/usb.h`, and port
62078 is its `.port = 0xf27e`.

**Where this driver deliberately differs, the difference is marked and
argued in the source.** There are exactly two:

- **the window is what this kernel can take** (1792 bytes), not
  usbmuxd's 131072, which would invite the overflow the advertisement
  exists to prevent. Derived from `MUX_BUF` in one place.
- **the device's SYN is acked at ISN + 1.** usbmuxd does `tx_ack++` from
  zero, which is right only because the ISN has always been 0 — an
  assumption that is unfalsifiable as written. Byte-identical for ISN 0,
  correct for anything else, and LOGGED when it is not 0.

Three of the five, and the most useful finding in the release, shared one
shape: **a refusal that is arithmetic rather than a named error code.**
Remove the length-field guard and `mux_recv()` returns `len - hdr` —
for a length of 4 and a header of 8 that is **-4, USB_ENODEV, "no
controller, or nothing on the port."** A four-byte length field would
have sent the next person to check whether the phone was plugged in. A
twenty-byte header read out of an eighteen-byte packet returns -2,
USB_ESTALL, "the device returned STALL" — it did no such thing. **Every
such test asserts the exact code now.** `x_control()` returning (3) for
six causes, in the one shape a return value can take it.

distinguish anything (`tcp_state` is 2 whether or not it reconnected —
the device counts SYNs now); a subject masked by a guard somewhere else;
a property that passed by luck (the scanner's anchoring — in the reply
used, the first "Type" sits inside "QueryType" and the next `<string>`

### ONE MODEL OF A PHONE, IN ONE FILE

**`tests/muxdev.inc`** is now the only simulated iPhone in the tree, and
both mux suites include it. Two copies of a device model drift apart,
which is what `tools/check_diskname_sync.py` exists to refuse;
`tests/blkbus.inc` is the same arrangement one layer down.

And it is **not a parrot.** It validates what arrives the way usbmuxd
does — a length field that does not match the transfer, a missing magic,
a header that is not five words, ports that are not this connection's,
**and a sequence number it was not expecting** — and records *why* it
refused. That last one is why it exists: the sequence arithmetic has no
screen of its own, and a device that shrugs at wrong arithmetic cannot
tell a correct driver from one that merely sends plausible packets.

**It is deliberately NOT stricter than the device in one place.** A zero
TCP checksum is counted, not refused, because usbmuxd never fills that
field and the device accepts it. A fixture stricter than the real thing
fails correct drivers, which is its own kind of lie.

### ANSWERED, 26 OCTOBER: "(3)" WAS THE EVENT RING

**Do not run `dmesg | grep xHCI` to chase this. It is found and fixed.**
The line would have named a completion code belonging to a different
device.

`usb cfg` reported *"the device would not describe it (3)"* for every
configuration of every device — including the webcam and the MediaTek
Bluetooth, which no driver has ever touched. The decisive photograph was
a **fresh boot of 0.8.7.4 with the phone attached, addresses 1/2/3, no
rescan**, with all six reads already failing. That killed "degrades over
rescans", and left the phone's presence as the only difference from the
healthy 10:18 boot.

**`evt_wait()` returned the next event of the right TYPE and never
checked which slot or endpoint it was for.** A transfer that times out
returns with its TRB still live; the controller finishes it later; the
event arrives with no waiter; the next synchronous caller — another
endpoint, another device — reads it as its own result. DHCP against an
untrusted phone timed out and abandoned several TRBs every boot, and the
six descriptor reads each took one.

Fixed in 0.8.7.5: `evt_pump()` is the ring's only consumer, events are
filed by owner (`ep_busy` or `ep_sync`), an event nobody owns is dropped,
and a timeout stops its endpoint instead of abandoning it. 310 tests, 82
injections. `CHANGELOG-v0.8.7.5.md` has the whole chain.

**The lesson worth keeping.** The old `evt_drain()` was written in
0.8.5.1 *because* the event ring is shared, and its comment says so. It
got the async direction right and then argued the synchronous direction
was safe because `x_data()` "runs to completion before any poll happens"
— while the comment forty lines above it stated that a timed-out
`x_data()` leaves its TRB live. **The tree contained both halves of the
proof and never put them together.** When two comments in one file
disagree, one of them is a bug.

Also: the two tests that proved `evt_drain()` left a foreign event alone
each ended by consuming it with an explicit `evt_wait()` so the next test
"starts clean". That hand cleanup was exactly what the real system never
does, and it hid this for three releases. **A test that tidies up after
the thing it is testing is testing the tidying.**

**Not the slot leak.** `out->addr` is read from slot context dword 3 --
the address the CONTROLLER assigned -- and an xHCI does not reclaim
addresses until reset, so a rescan handing out 4, 5, 6 after a boot
used 1, 2, 3 is expected rather than a leak.

## 0.8.7, and what the grep found

### THE BIGNUM, AND WHY IT IS TRUSTWORTHY

`include/bignum.h` + `net/bignum.c`, 0.8.8.1. 32-bit limbs, Montgomery
multiplication for `bn_modexp`, binary long division for `bn_divmod`,
Stein for `bn_gcd`, and the **division** form of extended Euclid for
`bn_modinv`. `tests/test_bignum.c` is 299 checks and
`tools/check_bignum_suite.py` catches all 18 planted defects.

`rsa_public_encrypt()` runs on it now. The old byte-wise
implementation is still in `net/tls_crypto.c`, renamed `bn_*` →
`obn_*` and marked unused on purpose — two bignums in one file both
called `bn_` is how the wrong one gets called, and it stays because it
is the only independent implementation of a modular exponentiation in
this tree. **It must not acquire a caller.**

**READ THESE TWO BEFORE WRITING ANY MORE ARITHMETIC.** The suite
failed on its first run, 273 of 277, and both failures were real:

1. **`bn_modexp` refused every 2048-bit modulus.** It formed
   Montgomery's `R² = 2^(32·2n)` as a literal; for a 2048-bit modulus
   that is `2^4096`, needing limb index 128 when `BN_LIMBS` is 128 and
   the top index is 127. A bound check turned it into an honest
   refusal rather than a write into the next static. **1024-bit modexp
   passed** — a suite that stopped there would have shipped green.
   `BN_BITS` is 4096 so that the *product* of two 2048-bit numbers
   fits **exactly**, with nothing to spare; anything that wants
   `2^BN_BITS` has the same problem.

2. **`bn_modinv` could not do the one inverse RSA needs.** It was the
   binary extended Euclid, which requires an **odd** modulus — and
   `d = e⁻¹ mod lcm(p-1, q-1)`, where the lcm of two even numbers is
   always even. **And the vectors agreed with the restriction**,
   because the generator wrote `| 1` on every modulus it produced. The
   generator now refuses to emit vectors unless at least one has an
   invertible value modulo an even modulus.

Both are the same shape: arithmetic correct on every size and parity
the fixture happened to contain. **That is the shape to watch for in
Miller-Rabin and keygen**, where the fixture is whatever candidate the
RNG produced.

Two more things worth carrying forward:

- **The expected answers come from CPython and `openssl genrsa`, never
  from `net/bignum.c`.** Regenerate with
  `python3 tools/make_bignum_vectors.py tests`. Wrong arithmetic here
  produces numbers that look exactly as random as right arithmetic,
  and RSA is self-consistent under a broken implementation: if modexp
  is wrong the same way in both directions, `m → m^e → ^d` still
  returns `m` and every server on the internet rejects the
  ciphertext. **The round-trip check is not what protects this. The
  known-answer vectors are.**
- **The generator caught a defect before the suite ran.** It asserted
  `d·e ≡ 1 (mod φ(n))` and OpenSSL failed it: RFC 8017 defines `d`
  against `λ(n) = lcm(p-1, q-1)`. `e⁻¹ mod φ` is also a working
  private exponent, so checking against φ would have failed a
  perfectly correct extended Euclid and sent the hunt into the kernel.
- **`bn_divmod` is binary long division because 64-bit division is a
  LINK ERROR here.** `__udivmoddi4` is in libgcc and libgcc is not
  linked into a freestanding 32-bit kernel. `fs/exfat.c` hit it in
  this same release and `make` caught it, not a suite — native builds
  divide 64-bit values for free. `check_bignum_suite.py` plants one
  and passes `make` as a build check, because that is the only place
  it shows up.

### MILLER-RABIN AND KEYGEN ARE DONE — AND READ THIS BEFORE TRUSTING
### ANY SUITE IN THIS AREA

`include/rsa.h` + `net/rsa.c`: trial division against the primes to
997, Miller-Rabin on top of `bn_modexp`, and RSA key generation as a
**state machine** that steps rather than blocking, so a keygen shows
progress and stays interruptible. `tests/test_rsa.c` is 361 checks
and `tools/check_rsa_suite.py` catches all 18 planted defects.

**IT SHIPPED WITH A LIVE BUG AND A SUITE THAT COULD NOT SEE IT.**

```c
    if(rounds == 0) rounds = 1;
    for(r = 0; r < 1; r++){        /* should be r < rounds */
```

`rsa_is_probable_prime(n, 64)` was a ONE-ROUND test. Measured on
2284453 = 1069 x 2137: 37 of 200 runs called it prime at one round,
29 of 200 at sixty-four. The extra witnesses were never drawn. Key
generation was unaffected — `rsa_keygen_step()` has its own witness
loop — so keys already made are sound.

**Why nothing caught it is the part to carry forward.** The suite
passed 295 of 295 and the harness reported TEN of eighteen injections
undetected. All ten lived in code the suite never ran:
`rsa_is_probable_prime()` proves primality below **997 x 997** by
trial division alone, and every Carmichael number and pseudoprime in
the vectors was below that bound. Miller-Rabin was unreachable.

`tools/make_rsa_vectors.py` now CONSTRUCTS the hard cases —
Carmichael numbers from Chernick's formula and strong pseudoprimes
built as p(2p-1), every factor above 997 — and refuses to emit any
that trial division could catch. **If you add a primality vector, it
has to be above 994009 or it tests a division table.**

Three more things that cost time here:

- **A strong pseudoprime to base 2 PASSES a Miller-Rabin round with
  witness 2.** That is what the words mean. A check that pins the
  entropy source at 2 and demands "composite" is asserting something
  false; it passed only because trial division refused the small
  vectors first.
- **A Carmichael number survives ONE random witness about a third of
  the time.** A one-round group demanding "composite" passes or fails
  with the PRNG.
- **A harness that cannot finish has proved nothing.** The p == q
  test arranges a collision by replaying the found prime, so every
  candidate survives all 64 witnesses before rejection, 20000 times —
  1.28 million 256-bit modexps. It took the suite from 30 s to NINE
  MINUTES and the harness past three hours, where it was killed. One
  witness in that block; the round count is asserted where it belongs.

**And never background an injection harness.** It was backgrounded
here because the tool call times out at ten minutes, and a `make`
that overlapped it built from an injected tree. The ISO was rebuilt
afterwards and `net/rsa.c` verified pristine, but that is luck, not
process.

### WHAT IS LEFT OF STAGE 3

A DER encoder, X.509 v3, PKCS#1 signing, and a plist writer, plus
PEM->DER base64 (the third base64 decoder in the tree, and the
release where they should become one). **A phone sharing its connection is not
promised by any of this** —
`docs/havendos-iphone-tethering-needs-pairing.md` is still the

**And this is what `kpoll_sleep_ms()` was built for.** A keygen on a
kernel where nothing ran on a timer was a frozen machine with no way
to tell a slow prime search from a hang. The keygen yields through the
polling sleep, shows progress, and stays interruptible. That was the
whole argument for doing Helios first and it still holds.

**The 15-25 minute figure is now wrong, in the good direction**, and
has not been re-measured. It came from the byte-wise `obn_powmod` at
0.073 s per exponent byte. Montgomery changes the inner loop
completely; a Miller-Rabin round on a 1024-bit candidate was about
2.3 s and will not be. **Measure it rather than quoting either
number.**

### WHAT THE NEXT PERSON SHOULD KNOW ABOUT kpoll

- **The tick sets flags. It does no work.** `include/kpoll.h` has the
  argument, and it comes down to every layer in this tree sharing
  module-level buffers that are not reentrant.
- **`kernel_poll()` may be called from two files**, and
  `tools/check_kpoll_sites.py` refuses a third. `kpoll_sleep_ms()` may
  not appear in `drivers/`, `usb/`, `net/` or `fs/` at all;
  `sleep_ms()` is the driver-safe wait and is unchanged.
- **Six entry points bracket themselves** with
  `kpoll_enter()`/`kpoll_leave()`, as four-line wrappers round
  unchanged inner functions. `tools/check_kpoll_guard.py` holds the
  list and refuses one that loses its bracket or returns before the
  leave.
- **If you add a client, register it from `kernel/main.c`** — the one
  place, so the list of everything this machine does on a timer is four
  lines in one file. The check refuses registration elsewhere.
- **`kpoll` prints the refusals by reason.** "a driver holds a shared
  buffer" is normal. "already polling" should stay at zero.

## The discipline this tree runs on

- **A suite that passes on its first run is the least trustworthy result
  available.** 0.8.7's three new suites all passed first time and their
  harnesses found **sixteen holes** between them; 0.8.8's two did the
  same and its four harnesses found **thirteen**. Two releases running,
  and the shapes repeat:
  - **A guard that cannot fire**, which no suite can report. Two in
    0.8.8: a refusal code no input could reach, and a flag nothing
    could set.
  - **A fixture that cannot produce the before-state**, so the
    transition it claims to test never happens.
  - **A fixture that cannot distinguish anything.** NICs registered with
    unit equal to index; two NICs sharing one bus word; a static
    transmit buffer that is already zero, so a missing `memset` is
    invisible until a real frame dirties it.
  - **A property masked by a guard somewhere else**, failing only in
    pairs — v0.8.6.7's two bugs again. Four of `test_netdev`'s seven
    were this, and the answer was to read the table directly and say so.
- **Count the WIRE, not the outcome.** 0.8.6's lesson and it kept
  earning its place: a two-byte receive yields a zero-length frame
  whether the driver refused it or counted it, so the counter is the
  test; a send to a receive-only NIC and a send the hardware refuses
  both return -1, so the driver's call count is the test.
- **A harness you trust instead of thinking has to be checked itself.**
  Every harness that uses `tools/inject.py` runs a *harmless* injection
  last and fails if it is reported as caught. **Eleven do not use it.**
- **An injection that proves not to be a defect is RECORDED, not
  deleted.** v0.8.6.3 proved two of ten; 0.8.7 proved two more. An
  injection deleted without a word is one somebody writes again.
- **Our code agreeing with itself is not evidence.** `fsck.vfat`,
  mtools, sgdisk, parted and `zlib.crc32` judge the results.
- **Byte-identity, not "it looks right."**
- **Simulation answers only the questions you thought to ask.**
- **When you add a bus, grep for every place that chooses one** — and
  make the grep mechanical. Three releases running, the dispatch was one
  layer below where the previous release guessed.

## Things that will bite you

- **A GUARD THAT CANNOT FIRE IS NOT A GUARD, AND A SUITE CANNOT TELL
  YOU SO.** v0.8.8's biggest finding and it came from an injection
  harness, twice in one release.

  `VGA_CELLS_MAX` was exactly `VGA_COLS_MAX * VGA_ROWS_MAX`, so no grid
  could be inside both axis limits and over the budget: `VGA_MODE_EBUDGET`
  was unreachable and `fbc_fit()`'s area clamp was dead code. 124 checks
  "covered" both and could not reach either. And `vga_grid_capped()`
  asked "was the last fit clamped" when `vga_set_mode()` validates
  everything BEFORE calling `fbc_fit()` — a flag that is never set
  cannot fail to be cleared, so the injection that stopped it being
  cleared was missed.

  Both were found by deleting the thing and watching the suite shrug.
  **A green suite over a guard says nothing about whether the guard is
  reachable.**

- **TWO WRITES THAT EACH MASK THE OTHER ARE TWO UNTESTABLE WRITES.**
  `usb/hotplug.c` recorded the port bitmap inside the change loop AND
  re-read it after the rescan. Delete either alone and the behaviour is
  identical, so an injection into either was missed. v0.8.6.7's
  failing-only-in-pairs shape, and four of `test_netdev`'s seven holes.
  The redundant one is gone; putting it back is recorded in
  `check_hotplug_suite.py` as **not a defect**, because the post-rescan
  reading overwrites it either way.

- **A FIXTURE THAT CANNOT PRODUCE THE BEFORE-STATE CANNOT TEST THE
  TRANSITION.** Two checks in v0.8.8 called `net_dhcp_retry_reset()`
  and then asserted the retry counter was zero, which it had never
  left. Both passed. Both were vacuous. The same shape as a wrap test
  starting at `0xFFFFFF00`, where `+100` does not cross zero.

- **A FIXTURE'S OWN REPORTING CAN CHANGE WHAT IT MEASURES.**
  `ck(..., kernel_poll() == KPOLL_EOFF, kernel_poll())` evaluates the
  `got` argument too, so it polls TWICE — and then asserted a refusal
  count of 2. It passed.

- **A LIVE LOG ECHO IS SAFE ONLY WHILE NOTHING ELSE OWNS THE SCREEN.**
  `klog`'s echo was fine for as long as every call came from a driver
  bringing itself up before anything was drawn. The moment a periodic
  client could log, a DHCP retry appeared on top of `dmesg`'s pager
  prompt. The echo is off after "System ready" now. **If you add
  anything that logs from `kernel_poll()`, it goes to the ring and
  `dmesg` is the view of it.**

- **A PAGER EATS THE NEXT COMMAND.** Two commands page and they use two
  different prompt strings: `dmesg` says `-- more -- (any key, Q to
  stop)`, `help` says `-- more -- press any key --`. A harness that
  does not page through leaves one open, and the next command's
  characters are consumed as the keys that dismiss it — `resolution
  reset` arrived as `ution reset` and the shell reported a command that
  does not exist, which reads nothing like an unread prompt. And
  testing for `-- more --` anywhere on screen is wrong: it stays
  visible after a key dismisses it, so it has to be the LAST line.

- **A SCREEN READER THAT DIVIDES THE PANEL BY THE GRID IS WRONG ON ANY
  PANEL THAT IS NOT AN EXACT MULTIPLE.** `harness/fbtext.py` computed a
  cell as `W//cols` by `H//rows`; `drivers/vga.c` picks an integer
  scale per axis and CENTRES the result. They agree on 1280x800 at
  80x25, which is the only panel QEMU has been run at here. On 1366x768
  the sampling point drifts a pixel per column.

- **AN ARGUMENT ABOUT ONE END OF A PROTOCOL IS NOT EVIDENCE ABOUT THE
  OTHER.** `usb/lockdown.c` accumulates a reply across packets because
  libimobiledevice's `internal_plist_send()` writes the length and the
  body as two separate `service_send()` calls. That is true, it is in
  the source, and it is about the HOST. **The device sends them
  together** — `reply: 301 bytes in 1 packets` on the HP — so the
  reason given for the code did not apply to the code's actual input.
  The code was right anyway, which is the uncomfortable part: a correct
  decision resting on a reason that does not hold is one nobody will
  re-examine. Same shape as the magic, one release earlier.

- **AN INJECTION IS A POINTER INTO SOURCE THAT MOVES.** Three releases
  running, a rewrite has left injections matching nothing or matching
  twice. v0.8.7.9's `lockdown_get_value()` builds its request instead
  of using a fixed string, so `<key>Label</key>`, the Request key and
  the not-connected guard each appear TWICE in the file now, and four
  previously-unique injections started matching both. `tools/inject.py`
  reports stale and multiply-matching injections rather than counting
  them as passes, and **that is the only reason they were not silently
  lost**. When you add a second caller of anything, re-run the harness
  before believing the suite.

- **AN INJECTION BEING CAUGHT SAYS NOTHING ABOUT WHETHER THE BEHAVIOUR
  IS RIGHT.** The most expensive lesson in the 0.8.7.x line, and it is
  about the harnesses rather than the code.

  `check_usbmux_suite.py` carried "a wrong magic is parsed around" for
  three releases. It was caught every run. **The guard it protected was
  wrong** — the device sends 0xFACEFACE where this host writes
  0xFEEDFACE, usbmuxd never reads the field at all, and v0.8.7.7
  refused the phone's SYN/ACK over it.

  A harness can only ask *would we notice if this changed*. It can
  never ask *should it be this way*. Both the suite and the fixture
  agreed the guard was right because both had taken the value from the
  same header — and the suite's own blurb listed "the magic really is
  0xFEEDFACE" among the things it pinned down.

  **So a green harness is not evidence about correctness, only about
  sensitivity.** When a guard has never run against real data, say so
  where it is written, and go and get the real data.

- **A GUARD YOU CARRY FORWARD IS STILL A GUARD YOU ADDED.** The magic
  check came from v0.8.7.3, was correctly re-scoped in v0.8.7.6, and
  had never once run against a packet from a device — stage 0 only ever
  received VERSION replies, which use the short header and skip it.
  v0.8.7.7's changelog lists two deliberate departures from usbmuxd and
  says every departure is marked and argued. This was a third,
  undeclared, because nobody re-examines a check that was already
  there. **When a new path makes an old guard reachable for the first
  time, it is a new guard.**

- **A SPURIOUS WARNING IS A DEFECT, NOT A STYLE POINT.** `dmesg | grep
  usbmux` is how every hardware question in this line has been
  answered. A line printed on every healthy packet buries the one that
  matters. Both mux suites count KLOG_WARN separately from log lines
  now and assert that a complete stage-1 exchange emits **none** —
  which is also the only thing that can still catch a magic check
  running during the VERSION exchange, where bytes 8..11 are the major
  version and the warning would read `magic 00000002` on every boot
  there has ever been.

- **A HARNESS IS NOT EXEMPT FROM THE RULES IT PROTECTS.**
  `harness/lockdown_boot.py` compared the screen against a version
  LITERAL and broke on the first bump. `make_version.py --check`
  refuses version literals in C sources for exactly that reason. It
  reads `include/version.h` now.

- **A REFUSAL MUST BE A NAMED ERROR CODE, NOT ARITHMETIC THAT WENT
  NEGATIVE.** The most useful thing 0.8.7.7's harnesses found, three
  times over. Remove a length-field guard and `mux_recv()` returns
  `len - hdr`: for a length of 4 and a header of 8 that is **-4, which
  is USB_ENODEV — "no controller, or nothing on the port."** A four-byte
  length field would have sent the next person to check whether the
  phone was plugged in. A twenty-byte header read out of an eighteen-
  byte packet returns -2, USB_ESTALL, "the device returned STALL" — it
  did no such thing.

  Every caller treats negative as failure, so the suite passed and the
  guard looked unreachable. **Assert the exact code.** This is
  `x_control()` returning (3) for six different causes, in the one shape
  a return value can take it, and it is invisible precisely because the
  wrong answer is still an error.

- **TWO WRONG VALUES THAT HAPPEN TO BE EQUAL LOOK EXACTLY LIKE A FIELD
  YOU CANNOT TEST.** `tests/test_usbmux.c` recorded, in so many words,
  that it could not tell `tx_seq` from `rx_seq` because both were 1 on
  the only packet carrying them, and said the check belonged at stage 1.
  It was right that the check was impossible and **wrong about why**:
  the two values are not 1 and 1 at all, they are 0 and 0xFFFF, and
  0.8.7.6 was writing two wrong numbers that coincided. A recorded gap
  is a hypothesis, not a finding — re-derive the expected values before
  trusting the explanation for why a field is untestable.

- **A FIXTURE STRICTER THAN THE DEVICE IS ITS OWN KIND OF LIE.** The
  mock-that-cannot-refuse is the famous half of this, and 0.8.7's
  Ethernet suite is its monument. The other half costs just as much: a
  simulated device that rejected a zero TCP checksum would fail a
  correct driver, because usbmuxd never fills that field and the phone
  accepts it. `tests/muxdev.inc` COUNTS the checksum and refuses the
  things usbmuxd refuses. Model what the device does, in both
  directions.

- **COPY WHAT WORKS; ARGUE EVERY DEPARTURE IN THE SOURCE.** usbmuxd is
  the only implementation known to work against this device. Its
  mux-level `rx_seq` handling looks pointless — it mirrors a field
  straight back and the device may well ignore it — and it is copied
  anyway, because a field nobody has PROVED is ignored is a field to
  copy. 0.8.7.7 departs from usbmuxd twice, and both departures are
  marked, reasoned and (for the ISN) logged at runtime. "More correct
  than the thing that works" is the position that cost 0.8.7.3 a
  release.

- **RUN THE HARNESS EVEN WHEN EVERY RESULT WILL BE A SHRUG.** One
  0.8.7.7 injection was genuinely unreachable — masked by the SETUP's
  reset. Establishing *why* meant asking what happens when the SETUP
  does not send, and the answer was that it was never sent again: a
  channel claiming a version the device had never agreed, reporting
  itself healthy for ever. **The bug was found by investigating a
  non-finding.**

- **BOOT IT. A SCREEN IS A DELIVERABLE AND IT CAN BE WRONG.**
  `harness/lockdown_boot.py` found that `usb lockdown` printed TCP-
  framing guidance on a machine with no iPhone at all — sending the
  reader to doubt a framing that was never reached. No suite checks what
  a shell screen says, and `x_control()`'s mistake is just as expensive
  in the shell as in the driver, because there it costs a trip to the
  laptop. 0.8.7 and 0.8.7.6 both shipped without the ISO being built;
  the tools install, and the command is at the top of this file.

- **A fixture written from the same misunderstanding as the driver
  agrees with it perfectly.** `test_usbmux` passed 79 of 79 against a
  sixteen-byte header the phone has never used, because the simulated
  device and the code under test were written by the same person on the
  same afternoon from the same guess. A suite can only disagree with the
  code; it cannot disagree with the world. **Where a protocol comes from
  outside this tree, get bytes off the wire into the fixture** —
  `test_usbmux.c` now has the literal twenty bytes the HP printed, and
  those cannot be wrong. The same hazard applies to anything modelling a
  device nobody here has read the specification for.

- **An ordering that makes a bug untestable is not a fix for it.** The
  0.8.7.6 `survey_cb()` first matched the Ethernet interface and
  returned, which meant a class-only match on the mux interface could no
  longer reach the wrong one. The existing injection went from caught to
  missed while the guard still read as present. `check_usbmux_suite.py`
  found it. **Run the harness after moving code, not only after
  changing behaviour.**

- **A shared queue makes any timeout everybody's problem.** One event
  ring serves every endpoint of every device plus the command ring, and
  until 0.8.7.5 a waiter took the next event of the right *type* without
  checking whose it was. A transfer that times out leaves its TRB live,
  so its event arrives later with no waiter and the next caller reads it
  as its own result. One unanswered DHCP write broke descriptor reads on
  a webcam. The rule now: an event is consumed before anything judges it,
  and filed only against an owner that said it was waiting (`ep_busy` or
  `ep_sync`). **If you add a third kind of waiter to that ring, it must
  declare ownership the same way.**

- **The compile-time IP default is QEMU's, and it looks like a working
  configuration.** `10.0.2.15` behind a gateway at `10.0.2.2`. DHCP ran
  once, at boot, and only if a NIC was already registered -- so a USB
  NIC plugged in afterwards came up holding an address its network had
  never heard of, with `ifconfig` reporting `Status: UP` over the top
  of it. The only symptom was `dns: resolution failed`.
  `usb rescan` asks for an address now, and `net_config_source()` makes
  every report say whether the address was negotiated or invented.

- **The xHCI back-end refuses a transfer bigger than its buffer, before
  the controller is touched.** `x_data()` bounds at `sizeof g_bounce[0]`
  and `x_intr_poll()` at `XHCI_ABUF_SZ`; both are 2048 now and were 1024
  and 64. A driver that asks for more does not fail slowly on the wire --
  it never reaches the device, and every counter it keeps reads like a
  dead link. `tools/check_usb_buffers.py` compares the driver constants
  and the simulated bounds against both.

- **A simulated back-end must be at least as STRICT as the real one.**
  `tests/test_usbnet.c` accepted a transfer of any length, so a driver
  that could not move a single frame passed 110 checks. That is the
  mock-that-cannot-refuse mistake `include/usb.h` has warned about since
  v0.8.5, one layer down: not a device that always succeeds, a
  CONTROLLER that always succeeds.

- **klog is not printf.** It does `%d %u %x %s %c %%` and ONE pad digit
  1-8, so `%4x` prints 00c1. Anything else -- `%02X`, `%04X`, `%ld` --
  is printed LITERALLY and its argument is NOT consumed, so every later
  specifier on the line silently takes the wrong one.
  `tools/check_klog_fmt.py` refuses them.

- **NEVER run the injection harnesses in a background process.** A
  harness DAMAGES the source on purpose and restores it in a `finally`.
  Kill the process part-way -- a timeout, a closed session, a container
  reaping background jobs -- and the restore never runs, so an INJECTED
  DEFECT is left sitting in the tree looking like real code.

  v0.8.7 shipped nothing because of it, but only just. The whole sweep
  was backgrounded, it was killed during `check_nvmerw_suite.py`, and
  `drivers/nvme.c` was left with the NVMe WRITE opcode changed from
  0x01 to 0x02 -- which is READ. `make` built it, the ISO built, and
  `make test` caught it: 66 of 83, with `nvme_write()` returning
  success while the controller logged reads.

  Two things saved it. `make test` can fail (v0.8.5.6), and the suite
  checks the WIRE rather than the return value -- the write "succeeded"
  on every one of those 17 failures.

  Run them in the FOREGROUND, one at a time, and if a run is ever cut
  short, diff the tree against the last source zip before trusting it:

  ```
  for f in tools/check_*_suite.py; do python3 $f; done
  ```

- **Two modules' `static int` of the same name MERGE, silently.** An
  uninitialised `static int g_ndev;` is a tentative definition, and C
  permits any number of them for the same object in one translation
  unit — so a suite that `#include`s both files gets ONE VARIABLE, with
  no error and no warning at any `-W` level. `usb/core.c`'s device count
  and `net/netdev.c`'s NIC count were the same `int` for an afternoon,
  and it took a sanitiser to place. `tools/check_statics.py` refuses it
  now. The arrays clashed loudly and took a minute.
- **A driver that collapses many faults into one error number blinds
  whoever reads it.** `x_control()` returned USB_EXFER -- which prints
  as "(3)" -- for every xHCI completion code but success, short-packet
  and stall. Six different causes, one number, and it sends you to the
  wrong one. `cc_name()` covers all 36 the specification defines.
  Rate-limit the data path (once per endpoint, cleared on success); do
  not rate-limit the control path, which is rare and is the one that
  answers questions.

- **A build-check opt-out marker must not be tested with `\s*\S`.** In C
  the character after a bare `/* foo-ok: */` is the `*` of the closing
  delimiter, which is non-space — so a bare marker silenced
  `check_blk_dispatch.py` and `check_bus_label.py` from 0.8.6 until
  0.8.7. `tools/csource.py::has_reason()` owns that now and all three
  checks call it.
- **A build check must not classify lines with `line.split("/*")[0]`.**
  `tools/csource.py` owns that too.
- **A file that does not include its own header has no prototype
  checking at all.**
- **A header can name a test file that does not exist.**
  `include/usb.h` refers to `tests/test_usb.c`; the walk is tested in
  `tests/test_xhci.c`.
- **Configure Endpoint is called twice now.** Anything added to
  `x_configure()` runs on a slot that already has rings. Drop flags,
  ring freeing and ring re-laying all exist because of that, and all
  three were invisible until the simulated controller was taught to
  honour the drop flags — which is the Disable Slot situation of
  v0.8.6.1 verbatim.
- **SOMETHING runs on a timer now, and it still does no work in the
  IRQ.** v0.8.8. `kpoll_tick()` counts and sets due flags;
  `kernel_poll()` runs the work from the keyboard's idle loop, and
  `tools/check_kpoll_sites.py` refuses a third call site. The bounded
  polls are all still there and still the right thing inside a driver:
  a receive that blocks is a shell that stops answering,
  `usb_bulk_poll()` exists for that, and `intr_poll` is endpoint-type
  agnostic so one op serves both.

  **`sleep_ms()` DOES NOT POLL AND MUST NOT.** It is the driver-safe
  wait. `kpoll_sleep_ms()` is the one that polls, and the build check
  refuses it anywhere in `drivers/`, `usb/`, `net/` or `fs/`.

  v0.8.7.7 adds three more bounded polls — the SYN/ACK wait, and
  lockdownd's reply — and the lockdownd one **resets its budget on
  progress**, because the reply arrives in at least two packets and a
  single budget spent across the whole exchange gives up part way
  through. A bounded poll that spends its whole budget is, at the
  keyboard, indistinguishable from a wedge: `harness/lockdown_boot.py`
  times `usb lockdown` for exactly that reason.
- **bConfigurationValue is not a descriptor index.** A device may number
  its configurations 1, 3, 4, 7 at indices 0, 1, 2, 3.
  `usb_dev_t::cfgidx` exists because deriving one from the other is
  guessing at a mapping the device never promised.
- **The pager key is `spc`, not `space`.**
- **Page with SPACE only.** `q` quits the shell to the desktop.
- **A QEMU USB stick needs a partition table.**
- **q35 + `if=ide` is AHCI, not IDE.**
- **A firmware set to RAID/RST mode hides NVMe entirely.**
- **Secure Boot must be off** — the loader is unsigned GRUB.
- **`-no-pie` on the driver suites.**
- **`-Iinclude` makes `<string.h>` the kernel's.**
- **A suite that compiles `fs/fat16.c` or `fs/fat32.c` needs
  `fs/blkdev.c` too**; include `tests/blkbus.inc` before the filesystem.
- **`BLK_NO_HW` / `NET_NO_HW`** keep the real back-ends out of
  `fs/blkdev.c` and `net/netdev.c` for a suite that registers its own.
- **A positional initialiser for a struct of function pointers**
  silently rebinds everything after an inserted member. Both
  `usb_hc_ops_t` tables are designated; keep them that way.
- **VM scripts must run in the background** (`nohup ... &`) and be polled.
- **Never `pkill -f` anything from a script** — walk `/proc/*/comm`.
- **Disk images fill the container.** Delete them between runs.
