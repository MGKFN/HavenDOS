## Where this is

**HavenDOS dual-boots beside Windows 11 on a real laptop.** Installed to a
Samsung MZVL8512HELU NVMe SSD under UEFI firmware on 18 October 2026, boots
from its own partition, and Windows still boots. That is the headline and
everything below is in service of it.

The guarantee, in the terms it is made and tested:

> Outside the new partition, **four sectors** are written: the two GPT
> headers and one sector of each entry array. Their LBAs are printed on
> screen before anything is written. Inside the new partition, everything —
> it is free space. On the EFI System Partition, files are **added**;
> nothing is deleted and nothing is overwritten without a verified copy.

That held exactly on real hardware. The four sectors the preview named were
the four sectors written.

Four releases got here:

- **0.8.2 "Bedrock"** — FAT32.
- **0.8.3 "Lodger"** — the additive installer: GPT writer, ESP writer,
  FAT16 geometry, the preview screen, the first end-to-end UEFI boot.
- **0.8.3.1** — AHCI, NVMe writing, the MMIO test seam, and the six bugs
  below.

## What the bare-metal test actually taught

Six bugs in one afternoon. **Five had survived 1636 checks and eight
injection harnesses.** They are worth listing as a group, because the
pattern matters more than any one of them:

| bug | why no test caught it |
|---|---|
| E15 on any disk over 2 GB | the whole-disk path had no test for the size it picks |
| `(VirtIO)` on the confirm screen | four screens each decided the label; only one was tested |
| no NVMe case in `fs/fat16.c` | no test ever booted an installed system from NVMe |
| a DVD-ROM shadowing the real disk | same gap; found in QEMU while fixing the one above |
| `isr_common_stub` passed no frame | nothing had ever read a panic screen critically |
| `irq_common_stub` passed no frame | nothing depends on IRQs; HavenDOS polls |

Three of those are the same mistake: **the installer has one block layer
and the filesystem has another, and only one of them got taught.** When you
add a bus, grep for every place that chooses one.

The last two are the same mistake too: a handler that takes a pointer, and
a stub that calls it without pushing one. Both had been wrong since the IDT
was written.

## What is NOT done, in the order it matters

1. **The idle panic is unexplained.** The laptop panicked once sitting at a
   shell prompt untouched. The broken IRQ frame pointer is the best
   candidate and is fixed; it has not been reproduced. If it recurs, the
   panic screen is now truthful — take the EIP and run
   `nm -n havendos.elf` to find the function.
2. **`update` cannot run on a modern laptop.** It reads from an **ATAPI
   CD-ROM**. No optical drive, no USB mass storage, no supported NIC means
   no upgrade path at all on that machine — only reinstall. An
   **ESP-based update** is the obvious fix: the ESP is FAT32 on the NVMe,
   HavenDOS can read it, and Windows can write to it with `mountvol`. This
   is the highest-value next feature.
3. **A second install is refused** with `ESP_E_BACKUP` when `BOOTX64.HDB`
   exists. Fix: if the current fallback is already our own loader, skip the
   backup instead of stopping.
4. **No firmware boot entry.** The entry had to be added from Windows with
   `bcdedit /copy {bootmgr}` → `\EFI\HAVENDOS\grubx64.efi`. Needs UEFI
   runtime services.
5. **AHCI has never run on real silicon** — the test laptop has no SATA
   controller at all.
6. **An installed system cannot install HavenDOS** — the two-pass build
   means its kernel carries no installable image.
7. **No USB mass storage, no xHCI**, so no install from or to a stick and
   no trackpad on the HP.
8. **The console still cannot express a 1080p grid.**
9. **Partitions are capped at 2047 MB** until there is a FAT32 formatter.

## The discipline this tree runs on

Five rules, each learned by something going wrong:

- **A suite that passes on its first run is the least trustworthy result
  available.** Every module gets an injection harness: real bugs put into
  the code, each of which the suite must notice. Every harness written so
  far found holes — FAT32 missed 10 of 26, ESP 8 of 16, the formatter 6 of
  21, the additive installer 9 of 21, AHCI 12 of 32.
- **A driver is tested against a controller that executes its commands**,
  not a mock that returns success. `tests/test_ahci.c` and
  `tests/test_nvmerw.c` are the template; `include/mmio.h` is what makes it
  possible.
- **Our code agreeing with itself is not evidence.** fsck.vfat, mtools,
  sgdisk and parted judge the results.
- **Byte-identity, not "it looks right."** Anything that writes to a disk is
  checked sector by sector, before and after.
- **And now: simulation answers the questions you thought to ask.** Six
  bugs in one afternoon on metal says the remaining ones are in the places
  no harness models — bring-up state left by firmware, devices that exist
  but are the wrong kind, and paths nothing depends on until they fail.

When a guard turns out to be redundant, that is **written down in the
harness** rather than papered over with an injection reporting a false
MISS. There are several; they are explained in place.

## Things that will bite you

- **q35 + `if=ide` is AHCI, not IDE.** Also: QEMU's q35 carries a DVD-ROM on
  that controller, which is how the ATAPI-shadowing bug was found.
- **A firmware set to RAID/RST mode hides NVMe entirely.** BIOS setting, not
  a kernel bug.
- **Secure Boot must be off** — the loader is unsigned GRUB. On a BitLocker
  machine, suspend protection before changing it or Windows will ask for the
  recovery key.
- **`-no-pie` on the driver suites**, so a static array's address still fits
  the `uint32_t` a register holds.
- **`-Iinclude` makes `<string.h>` the kernel's.** Suites must not redeclare
  `memset`.
- **VM scripts must run in the background** (`nohup ... &`) and be polled.
- **Never `pkill -f` anything from a script** — it matches the script's own
  command line and kills the shell (exit 144). Walk `/proc/*/comm` instead.
  This is written in the notes and was still got wrong twice in one day.
- **The shell's pagers eat scripted keystrokes.** `help` pages; typing a
  command straight after it loses most of the characters.
- **`tests/gptdisk.inc` is source, not generated.**
- **Disk images fill the container.** Delete them between runs.

## Build checks that fail the build

`make` runs five, beyond `make test`:

| check | what it refuses |
|---|---|
| `check_efi_embed.py` | a kernel with no UEFI loader in it, or only one copy |
| `check_screen_width.py` | a string literal written past column 80 |
| `check_boot_log.py` | invented boot output |
| `check_help.py` | a command that dispatches but is not documented |
| `check_iso_version.py` | an ISO whose kernel and version.txt disagree |

## The test laptop, for reference

HP, Alder Lake (`8086:4601` host bridge, 51xx PCH), 16 GB RAM.
NVMe `144D:A80D` Samsung MZVL8512HELU-00BH1, 488386 MB, 512 B blocks.
xHCI only (`8086:51ED`) — no UHCI, so no USB input or storage in HavenDOS.
No SATA controller at all. NIC `14C3:7902` (MediaTek), unsupported.
Windows 11 25H2 on a 4-partition GPT; HavenDOS went into a 1024 MB gap
between C: and the recovery partition.
